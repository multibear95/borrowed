The dress is unavailable from the 16th to the 24th for four days of wear. That ratio is why availability is worth computing instead of guessing — and it is the most convincing number in the pitch. Leg values are the catalogue's own: delivery_days 1 · rental_days 4 · return_days 2 · cleaning_days 1, plus one day of buffer, baked in and never shown.

VocabularyThe two roles, fixed for the whole project

These words everywhere — prose, code, UI copy, prompts, tool descriptions — and never the old ones.

TermWhoPreviously
borrowerthe person who rents a garment for an occasion — Mirarenter
lenderthe person who lends her garment out — Lenaowner, then renter

The pair reads correctly in plain English with no gloss, which is the point: a borrower borrows, a lender lends, and neither word needs explaining to a judge or a definition printed beside it in the UI. renter is retired outright — it was ambiguous in both directions and should not appear anywhere.

  • One carry-over: catalog.json still uses owner_id, owner_name, owner_city and owner_rating. Those are real keys in a real file and are left untouched on purpose. Map them to lender_* in the loader, in one place, so the seed stays as it is and nothing downstream ever sees the old word.

The decision everything follows fromThree layers, split by what has to be true of them

SPEC §1.1 makes one load-bearing claim. An architecture either enforces it structurally or it doesn't — prompt discipline is not a substitute.

LayerWho does itProperty required of it
Deterministic corepure Python functions — no LLM, no I/Ocorrect, unit-tested, reproducible without a database
Tool boundaryone registry; hard constraints applied insideunbypassable — no caller can opt out
Conversational shellLangGraph + Claudefluent, recoverable, replaceable
  • Availability is a pure function. It runs with no database and no model, which is exactly why it can be trusted — and demonstrated live.
  • The tool layer filters; callers only present. search_garments returns only feasible garments, so no agent — ours or a stranger's — can offer a dress that cannot arrive.
  • "It asks before it searches" is an edge in a graph. A model that forgets is a product failure. A graph that cannot take the edge is a guarantee.

Four rules the frontend does not get to break

  • The server owns slot state. The browser holds a conversation_id and a message list. Two state machines that must agree is the bug that eats Sunday morning.
  • No date arithmetic in the browser, not even for display. ship_by, lands_on and free_again arrive as ISO strings. The moment the UI computes a date, "computed in exactly one place" stops being true — and that sentence is the pitch.
  • No model calls from the browser. Keys stay server-side and the graph stays the only orchestrator.
  • The borrower's reference photo never reaches storage. Read into vocabulary, then dropped. Enforced at the endpoint — and the frontend must not helpfully cache it.

03 · The engineA rental is two journeys, and only one of them is visible

Pure functions. No session, no model, no clock except a parameter. First thing built, and the only thing with real test coverage.

BUFFER_DAYS = 1        # baked in, never shown to the borrower

ship_by     = wear_date − delivery_days − BUFFER_DAYS
lands_on    = ship_by + delivery_days        #  ==  wear_date − 1
back_by     = return_date + return_days
free_again  = back_by + cleaning_days

hold(request) = [ ship_by , free_again ]     # the whole footprint
hold(booking) = [ b.ship_by , b.free_again ]

feasible  ⟺  today ≤ ship_by
          ∧  hold ⊆ [available_from, available_to]
          ∧  ∀ b ∈ bookings :  hold ∩ hold(b) = ∅
          ∧  requested_sizes ∩ sizes_eu ≠ ∅
          ∧  garment.city = request.city

Every refusal is an enum, never prose

TOO_LATE_TO_SHIP OUTSIDE_LENDER_WINDOW OVERLAPS_BOOKING IN_CLEANING SIZE_MISMATCH WRONG_CITY

IN_CLEANING earns its own value for one reason: it lets the UI say cleaning and lets the agent say "it's back from the wedding on Monday but not out of cleaning until Wednesday" — SPEC's low-cost realism point, delivered from data rather than flavour text.

The model receives {reason, ship_by, lands_on, free_again} and writes a sentence. It is explaining arithmetic it did not do and cannot override.

What the data model owes the operations

delivery_days, return_days, cleaning_days and condition_note are not estimates we invented — they are what SPEC §4 says logistics, cleaning and inspection actually take. That is the difference between a modelled domain and made-up numbers, and it is the sentence to use when a judge pushes. Image rows of kind original are never updated or deleted: they are the evidence record the cover mechanism depends on.

No vector store. A hard filter over the 386 records is a list comprehension running in under a millisecond, and on the hero query it cuts 386 down to 24. The hard filter is not a preliminary step before the interesting part — it is what keeps the interesting part cheap enough to be one LLM call.

03a · The storeJSON, and that is a decision rather than a shortcut

Runtime is in-memory. JSON is the seed and snapshot format — not "read the file on every query."

PieceRole
backend/data/catalog.jsonread-only seed, in git — 386 records, ~500 KB
backend/data/state/bookings.jsonwritten at runtime — new bookings only
backend/data/state/listings.jsonwritten at runtime — garments published during the demo
bootload → Pydantic models with real date fields → dicts keyed by id
readslist comprehensions over ≤50 objects
writesmutate memory, then atomic snapshot — tmp + os.replace()
resetdelete data/state/

Why it costs the architecture nothing

  1. The availability engine is already store-free — no session, no clock except a parameter. Swapping the store touches layer 4 and nothing else.
  2. Nothing in the query path needs SQL. A vector store was already rejected; a hard filter over 386 records is a sub-millisecond list comprehension.
  3. No database constraint was load-bearing. The overlap check lives in the pure domain layer on purpose, so Postgres was not enforcing anything we lose.

Never rewrite catalog.json on a booking

rule

Runtime writes go to the small state/ files and are merged over the seed at load. Rewriting 500 KB on every booking is wasted work, and it widens the window in which a killed process leaves a corrupt file — the file it would corrupt being the entire catalogue.

An honest correction to the case for JSON. At 386 records and 500 KB, "hand-edit the seed during rehearsal" is no longer the clean lever it would be at 15 records. Make today an injectable parameter instead — the engine already takes no clock except a parameter, so a --demo-date flag shifts the entire demo without touching data. Editing one lender's booked block stays easy; shifting the demo date should not require editing anything at all.

The write path — booking is real, so this is the part that must be right

Booking ships this weekend on both sides, so writes come from two places — create_booking and publish_listing — and a booking must block every other borrower immediately. The first risk is no longer file corruption. It is time-of-check / time-of-use.

WRONG   feasibility check … then  lock → write → unlock
        both requests pass the check, then both write. Double booking.

RIGHT   lock → re-check feasibility → commit → snapshot → unlock
        one critical section covering check AND commit.

Concurrency safety comes from the critical section, not from the storage engine — which is exactly why JSON is not weaker than SQLite here.

Six conditions, ordered by how much damage each prevents

  1. One asyncio.Lock wrapping feasibility re-check + commit, shared by both write paths.
  2. Pin uvicorn --workers 1. Two workers means two in-memory states and silent double bookings. One container was already the choice for SSE, so this costs nothing — but pin it explicitly, or someone optimises it on Sunday.
  3. Atomic writes — temp file plus os.replace(). A truncated JSON file from a process killed mid-write is unrecoverable at the worst possible moment.
  4. Snapshot on every commit, not on shutdown. If a booking is made on stage and the process restarts, that booking must still be there — otherwise the demo contradicts its own central claim.
  5. An idempotency key on create_booking. A double-tap on a phone is now a real double-booking path.
  6. Parse dates exactly once, at boot. JSON has no date type and this product is entirely date arithmetic; str versus date is the worst bug available here. Through Pydantic it comes out safer than raw driver rows.

The one thing Postgres could do that JSON cannot

Make double booking structurally impossible rather than code-enforced:

EXCLUDE USING gist (garment_id WITH =, daterange(ship_by, free_again) WITH &&)

Worth knowing, deliberately not done. It duplicates logic that lives in the domain layer by design, so it is a belt-and-braces measure — not a reason to run a database for a demo.

Payment stays out; the hold is real

wording

This is not a fake booking — the garment genuinely disappears from everyone else's results. Only the money is absent. The UI and the MCP tool description must both say reserved · no payment taken. A real hold misread as a paid rental is a trust problem, not a copy problem.

How to say it on stage: "an in-memory store behind a repository interface — Postgres is a config swap." Not "we used a JSON file." Keep the repository interface identical to what a SQLAlchemy version would expose, and Postgres becomes a day-one task afterwards rather than a rewrite.

04 · Agent graphsThe gate is four lines of Python, and it is the product

LenderGraph, and the map that makes corrections win

Photo → persist original → one multimodal call producing the full draft JSON → draft card → user replies in plain language → LLM emits a JSON patch → code merges it. State carries provenance: {field: "vision" | "user"}, and that map — not a prompt instruction — is what makes "the correction always wins" mechanical. It also drives the from photo / you said badges and the size_unverified flag.

Graph state is JSON and persists to conversations.slots. Printable state is worth more than any other debugging affordance on a hackathon weekend, and it is also what explain_availability and a state dump expose to a judge.

Five rules that make the boundary trustworthy

  1. Hard constraints live inside search_garments. There is no include_infeasible flag and there never will be. A third-party agent cannot surface a dress that misses Friday even if its own prompt tells it to.
  2. Every result carries the arithmetic. ship_by and lands_on ride along on each match, so any caller's explanation is grounded in our numbers.
  3. No tool returns prose. Reasons are enums plus dates. Sentence-writing is the caller's job — which is precisely why a foreign agent's sentences come out as truthful as ours.
  4. Reference photos never cross as a stored ref. style_hints are already-extracted vocabulary tokens, so "used and discarded, never stored" survives the boundary by construction.
  5. create_booking writes a real hold and takes no money — the description says both, in words. The garment genuinely vanishes from everyone else's results; only payment is absent. A vague description lets a foreign agent imply the rental is paid for, which is a trust problem rather than a copy problem.

Auth is an API key mapped to a scope set: default keys read-only, booking:write issued separately and rate-limited, writes idempotent on a caller-supplied key.

The cost of binding in-process, and the fix

Our own traffic never exercises the MCP transport, so a serialisation bug can hide until a judge plugs in Claude Desktop. One contract test closes it: run every external=True tool through the HTTP server against the same fixtures the unit tests use. Twenty minutes, then leave it in CI.

Someone installs MORE in their own Claude and asks "can any of these reach me by Friday?" — and gets an honest answer from a service they have no prompt control over.

That reframes the weekend from a chat UI over a catalogue to a deterministic availability service with a conversational client — a considerably harder thing to have built in two days.

06 · Image pipelineBeside the request, never inside it

  1. Segment the garment onto a consistent neutral ground — the same off-white for every listing.
  2. Normalise crop, aspect and scale so a grid reads as a collection instead of a classifieds board.
  3. Correct exposure and white balance. Not cosmetic: wrong white balance produces the wrong colour, and colour is a filter field. A navy dress shot under tungsten becomes unfindable.
  4. Write a full-size listing image and a 400px thumbnail.
  • Extraction always runs on the original. Any colour processing upstream of extraction produces the bug where the photo shows bright blue and the match was computed as navy.
  • Publish never waits. A 10–20 second upload stall kills the demo. The original is the cover until the normalised version replaces it; on failure it silently stays the cover.
  • Normalise presentation, never the garment. No colour deepening, no fabric smoothing, no removing a pull or a stain. Crossing that line turns a rental service into a misrepresentation.
  • The corrected colour is confirmed by the lender before publish, and condition is always declared in words rather than inferred from a clean-looking photo.

One asyncio queue in the same process is enough at this scale. No Celery, no Redis — not this weekend.

The cheap win on the lender side

SPEC §4.1: the lender is told her ship-by date, not asked for one. One line on her garment card — ship by Wed 16 Sep — closes the loop from borrower booking to engine arithmetic to lender action. A few lines of code for a complete causal chain a judge can watch happen.

The strongest moment in the demo

Two browser windows side by side. Book in one; the dress disappears from the other's results in the same second. SPEC §3.2 step 8 stops being a sentence in a document and becomes something done on stage. It needs both windows on the same process — condition 2 in The store — and it needs rehearsing, because it is also the moment a double-booking bug would surface.

The dress the demo script names is one the engine refuses

blocking

SPEC Scenario A has Lena declaring her gown "booked the 20th to the 25th"; Scenario B rents that same gown for a Friday-the-18th wedding.

The catalogue reproduces the collision slightly differently: item-0000 belongs to Lena and carries booked: 2026-09-16 → 2026-09-21, squarely across the hero window. It comes back OVERLAPS_BOOKING — one of the 19. The script's line "one of them was listed by Lena an hour earlier" is currently false.

Fix — pick oneMove item-0000's block clear of the window (27 Sep → 2 Oct makes it feasible, lands_on = Thu 17 Sep, verified). Or rewrite Scenario A around whichever of the 24 feasible dresses you want on screen, and give that one to Lena. The second is better — it means the demo reads the data instead of the data being bent to the demo.

booked semantics are undefined — decide this first

blocking

Nothing says whether a booked range is the wear window the lender declared or the full hold including shipping, return and cleaning. The two readings differ, and not by a rounding margin:

Hamburg EU 38 dressesread rawexpanded by the legs
Fri 18 Sep24 feasible22 feasible
Fri 25 Sep58 feasible34 feasible
Fri 2 Oct58 feasible38 feasible
RecommendationTreat booked as the wear window and expand it on load into hold_from = from − delivery_days − 1 and hold_to = to + return_days + cleaning_days. Block lengths run 2–6 days, which reads as wear periods rather than footprints; an lender declares the days she needs the dress, not the days the platform needs it; and it is the conservative reading, so the failure mode is "one fewer dress shown" rather than "double-booked". Whichever way it goes, write the decision into the loader — the same expansion has to apply when a new booking is written, or the two disagree.

delivery_days = 2 kills the hero query

closed by the data

Previously flagged as blocking. The catalogue splits delivery_days across 1, 2 and 3, and 43 of the Hamburg EU-38 dresses ship in a single day, so the hero query survives — and the 2s and 3s are exactly what produce the 72 TOO_LATE_TO_SHIP refusals.

ResolutionNo change needed. Do not normalise delivery_days to one value to "fix" the refusals — the spread is the most valuable property in the file.

Two feasibility clauses have no data behind them

resolve

available_from / available_to exist on no record, so hold ⊆ [available_from, available_to] compares against nothing. And formality does not discriminate: 378 of 386 records are 4 or 5, so Mira's "quite formal" removes eight items from the catalogue.

ResolutionDefault the availability window to today … today + 120d on load, or drop the clause and say so. Use formality for ranking only — never for hard filtering, and do not ask the borrower for it as though it narrowed anything.

Nulls the filters must tolerate

resolve

colour_family is null on 88 records, 18 of them dresses; silhouette null on 41; style_tags empty on 112.

ResolutionTreat null as unknown, do not exclude. A missing colour must cost a dress ranking points, never remove it from a query that mentions a colour — excluding on null silently shrinks the catalogue by a quarter.

Image provenance — decide before anything is public

decide

Every record carries a source_url and an image_url pointing at a live commercial rental site, plus rental_price_try beside the euro price. The images are mirrored into backend/images/, so nothing is hot-linked at runtime — but dress-rental-prd.md §14 asks for imagery that avoids copyright risk, and third-party product photography with the original product URL attached does not meet that on its own.

Options, least work firstKeep the data private to the demo and say plainly on stage that the catalogue is scraped placeholder content. Or swap the dozen garments that actually appear on screen for own or openly-licensed photographs and leave the rest as unshown filler. Either is fine; a public deployment that serves them without comment is not.

SPEC contradicts itself on the delivery floor

resolve

§2.4 says "three days is the floor"; Scenario B is two days out.

ResolutionThe engine has no floor. It computes and answers honestly, including "no". Three days is a targeting claim about who the product is designed around — implementing it as a constraint would reject the spec's own hero query.

The buffer is specified twice

resolve

§4.1 says both ship_by = wear_date − delivery_days and "one day of buffer is baked in".

ResolutionPick ship_by = wear_date − delivery_days − 1. That is what makes "arrives Thursday for a Friday wedding" true, and it is what every number on this page assumes.
